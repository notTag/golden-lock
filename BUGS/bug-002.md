# [002] Tamper guarantee relies on the CI .lock-diff tripwire, not the local lock — undocumented

- Status: done
- Created: 2026-06-12
- Severity: high
- Bump: minor

## Resolution
Done in `e6548ab`. README.md now documents what survives a clone, the limits
of same-commit hash verification, and the need for branch protection plus human
review of manifest diffs.

## Repro
1. On machine A, run `sudo golden-test lock test_x.go`. The file and
   `golden-test.lock` become root:0/444. Commit and push.
2. Clone the repo fresh (machine B, or CI). Observe ownership/permissions:
   the files come back owned by the cloning user with normal modes.
3. As that user, edit the golden file AND update its hash in
   `golden-test.lock` in the same commit. Run `golden-test verify`.

## Expected
A user reading the README should understand exactly what protection survives a
`git clone` and what does not, so they don't assume the 444 lock travels with
the repo.

## Actual
`chown root:0` + `chmod 444` is a local filesystem property; git stores neither
ownership nor permission bits (only the executable bit). After any clone, the
golden files and the manifest are ordinary writable user files. The durable
protection is therefore only the CI hash gate — and because `golden-test.lock`
is itself committed, a commit that changes a golden file *and* its recorded
hash together passes `verify` green. The real CI defense is a **tripwire**: it
forces a visible `golden-test.lock` diff into the PR, which only matters if
branch protection is on AND a human reviews `.lock` changes. None of this is
stated in the README, so the tool can give a false sense of cryptographic
immutability.

## Notes
Not a code bug — a documentation / threat-model gap. Fix: add a "What survives a
clone" section to README.md spelling out (a) local 444 protects only the
machine where `lock` ran, (b) the CI gate is the portable guarantee, (c) it is
a tripwire requiring branch protection + human review of `.lock` diffs. ARCH.md
already implies this but the user-facing README does not.
