# [003] Repo-root discovery diverges between lock (root) and verify (non-root)

- Status: open
- Created: 2026-06-12
- Severity: med
- Bump: patch

## Repro
1. Create a repo with `.git` at the top level and a `golden-test.lock` in a
   subdirectory (or a nested `.git` in a subdirectory).
2. From that subdirectory, run `sudo golden-test lock <file>` (root path).
3. From the same subdirectory, run `golden-test verify` (non-root path).

## Expected
`lock` and `verify` resolve the same repo root, so verify finds and checks the
manifest that lock wrote.

## Actual
`FindRepoRoot` (lockfile.go:57-106) takes two different routes by privilege:
under root it skips the git probe and walks ancestors looking for `.git` OR
`golden-test.lock` (whichever appears first per directory); when unprivileged
it prefers `git rev-parse --show-toplevel`. A stray subdirectory
`golden-test.lock` or nested `.git` can make the root-time root and the
verify-time root different directories, so verify can report exit 3 (manifest
absent) against a populated lock, or resolve a different root entirely. Normal
repos (single manifest at the git top level) are unaffected.

## Notes
Low likelihood in practice but a genuine correctness divergence. Options:
(a) use the same discovery strategy regardless of privilege, or (b) add an
explicit `--lockfile` / `--root` flag to bypass discovery (ARCH.md already
floats this). Document the chosen resolution order either way.
