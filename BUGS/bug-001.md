# [001] Privileged lock/unlock path has zero CI coverage

- Status: open
- Created: 2026-06-12
- Severity: high
- Bump: minor

## Repro
1. Inspect `goldentest_test.go`: the four tests that cover the privileged code
   (`TestLockUnlockFile_AsRoot`, `TestRunLock_FreezesBeforeRecording`,
   `TestDispatch_LockMalformedManifestAborts`, `TestDispatch_UnlockNotListed`)
   all begin with `if os.Geteuid() != 0 { t.Skip(...) }`.
2. Inspect `.github/workflows/ci.yml`: the `test` step runs `go test ./...` as
   the default (non-root) runner user.
3. Run the suite locally as a normal user (`go test ./...`).

## Expected
The code that establishes the security guarantee — `runLock`/`runUnlock` and
the calls beneath them: `LockFileFD` (fchown root:0 + fchmod 444), the
freeze-then-hash ordering, malformed-manifest abort, and the unlock membership
check — should be exercised by CI so a regression is caught.

## Actual
Those four tests `t.Skip` whenever the process is not root. CI runs non-root,
and local dev runs as uid 501, so the privileged path is effectively never
executed by the test suite. A regression that reintroduces a known prior bug
(e.g. reordering freeze/hash → REVIEW.md #3, or routing chown through a path
instead of the resolved fd → REVIEW.md #2) leaves CI green: `lock` still
"succeeds" and files still end up root:0/444, but the recorded hash no longer
describes the bytes that were frozen.

## Notes
This is a regression-net gap, not a flaw in the kernel-enforced security model.
GitHub's `ubuntu-latest` runner has passwordless sudo, so the fix is cheap:
add a `sudo go test ./...` step (or a dedicated privileged job) to ci.yml so
the root-gated tests actually run. Caveat: under sudo the whole suite runs as
root, so any test that assumes non-root (e.g. `TestDispatch_LockNotRoot`,
asserting exit 4) likely needs an inverse `if os.Geteuid() == 0 { t.Skip }`
guard. Verify those guards exist before wiring the sudo run in.
