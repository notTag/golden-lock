# [006] Empty-manifest cleanup uses path-based os.Remove, bypassing the dir-fd resolver

- Status: open
- Created: 2026-06-12
- Severity: low
- Bump: patch

## Repro
1. Lock a single file, then `sudo golden-test unlock` it so the manifest becomes
   empty.
2. Observe `runUnlock` (main.go:254-255) removing the now-empty manifest with
   `os.Remove(m.Path)`.

## Expected
Every privileged filesystem mutation goes through the symlink-free,
dir-fd-pinned machinery the rest of the code uses (`Openat`/`Renameat`/
`Unlinkat` on a verified directory fd), so no path string is re-resolved at the
moment of the privileged operation.

## Actual
The emptied-manifest removal is the one mutation that uses a path-based
`os.Remove(m.Path)` instead of `unlinkAt` on the verified repo-root dir-fd. It
re-resolves the path after the per-file resolver loop has already run, leaving a
very narrow TOCTOU window versus a parent-directory swap. Risk is low (the repo
root was already walked symlink-free earlier in the call), but it is
inconsistent with the otherwise-meticulous dir-fd discipline.

## Notes
Fix: open the repo-root dir-fd via the existing helper and `unlinkAt(dirFD,
LockfileName)` instead of `os.Remove(m.Path)`, matching the
`WriteManifestLocked` Renameat path.
