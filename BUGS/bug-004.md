# [004] Manifest hash field is never validated → corruption misreported as tampering

- Status: open
- Created: 2026-06-12
- Severity: med
- Bump: patch

## Repro
1. In a valid `golden-test.lock`, corrupt one entry's hash so it is still a
   single whitespace-separated token but not a valid digest (e.g. truncate it,
   or uppercase it).
2. Run `golden-test verify`.

## Expected
A structurally invalid manifest entry is a corrupt trust anchor and should be
reported as malformed (exit 3, "absent or malformed"), distinct from a real
content mismatch.

## Actual
`ReadManifest` (lockfile.go:235-245) only splits each line into
`(hash, path)` on the first whitespace run; it never checks that `hash` is 64
lowercase hex characters. A corrupt-but-parseable hash is accepted as a valid
entry, then surfaces during verify as `StatusMismatch` (exit 1, "hash
mismatch") — i.e. corruption is misclassified as tampering. The operator is
told a golden file was changed when in fact the manifest line itself is
damaged.

## Notes
Cheap fix: validate the hash token at parse time (`len == 64` and all chars in
`[0-9a-f]`); on failure return `ErrManifestMalformed` like the other malformed
cases. This also tightens the malformed-manifest abort on the lock path.
